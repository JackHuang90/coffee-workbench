# Offline web-export → device-target converter

`tools/curve_to_protocol.py` closes the **data-format** path from the existing Vue console's v1/v2 JSON exports to this firmware's tested core. It never opens USB, serial, sockets, or a browser, and it never emits ARM, START, a physical pin map, SV writes, PID tuning, or actuator commands. No published UI integration is claimed. Both supplied firmware images still lack physical actuator bindings.

## Prepare a target without contacting any device

From repository root (Python 3.9+):

```sh
python3 firmware/tools/curve_to_protocol.py saved-curve.json \
  --confirm-charge > target-preview.json
```

Read `origin_seconds`, `duration_ms`, `source_label`, `count`, `hash`, and `ignored_fields` in the preview. `--confirm-charge` explicitly confirms that the single CHARGE marker is the intended timeline origin. If there is no reliable CHARGE marker, select an existing sample time explicitly:

```sh
python3 firmware/tools/curve_to_protocol.py saved-curve.json \
  --origin 12.5 > target-preview.json
```

An origin between samples is rejected; this tool does not invent an interpolated origin BT. A library export (`format: coffee-roasting-library`) also requires `--curve-id EXACT_ID`, even if it currently contains only one curve. Direct curve exports need no selection.

## Inert staged-upload transcript

First read `HELLO`/`STATUS` from a **virtual-demo** build and use its current boot session and `last_seq + 1`. Choose an absolute device `uptime_ms` deadline at most 5000 ms ahead, modulo 2^32. These are device monotonic times, not host wall-clock timestamps.

The example numbers below are **illustrative and not reusable credentials or valid device state**:

```sh
python3 firmware/tools/curve_to_protocol.py saved-curve.json --confirm-charge \
  --emit commands --session 4242 --first-seq 1 --deadline 6000 \
  > upload-transcript.txt
```

This emits `BEGIN`, numbered `POINT`s, and `COMMIT`, each in an `R1` envelope. It still performs **no device I/O**. A saved transcript quickly expires; a future live bridge must obtain current session/sequence, refresh each deadline as needed, verify every ACK, and stop on any failure. Uploading many points may exceed one 5-second deadline. Do not blindly replay transcripts or assume success after a transport timeout. Read status and reconcile first. Hash/ID identify the committed target; ACK is software acceptance, not physical feedback. Manual explicit ARM/START is separate and only works in the virtual build. LOCKED rejects upload/control regardless of supplied values.

## Validation and deliberate omissions

- Input maximum 2 MiB, strict UTF-8 JSON, duplicate keys and JSON NaN/Infinity rejected. Accepts web schemas 1 and 2; data source is retained as a label, not relabelled as physical measurements.
- Every original sample must have finite numeric seconds and BT. Booleans, numeric strings, missing/null BT, gaps greater than 5 seconds, duplicate/descending times and malformed samples reject. ET is never substituted for BT. No downsampling, gap filling, smoothing, or tuning inference occurs.
- Origin must exactly match a sample. Selected samples become relative milliseconds from zero: 2–1024 points, ≤30 minutes, each gap ≤5000 ms, BT within -20..280 °C. Sub-millisecond timestamps reject rather than silently collapsing points.
- BT quantizes to nearest 0.1 °C, ties away from zero (`-1.25 → -1.3`). Validation checks the original temperature before quantization. FNV-1a32 covers little-endian uint32 milliseconds followed by little-endian int16 deci-Celsius for every point. This detects accidental corruption; it is **not authentication**.
- Safe web IDs of ≤24 letters/digits/underscore/hyphen are retained. Other valid web IDs become `curve-` plus 16 SHA-256 hex characters of the source ID. Original ID remains in the preview; checksum still covers the actual point data.
- Names, notes, weights, timestamps, ET, marker metadata and all non-CHARGE markers are reported as ignored. They cannot execute actions. In particular, DROP does **not** automatically stop the curve: the target runs to the last selected sample. Trim an export explicitly if a different endpoint is intended.
- `--emit commands` requires explicit uint32 session/deadline and positive sequence; sequence overflow rejects. Maximum command line length is checked against the firmware's 255-byte limit.

## Reproducible tests

```sh
mkdir -p firmware/build
python3 firmware/tests/test_converter.py -v
```

The test fixture `tests/fixtures/web-demo-v2.json` is an exact export generated by the existing application itself, not a firmware-specific invented schema:

```sh
node --input-type=module -e \
  "import {createDemoCurve} from './src/core/simulation.ts'; import {exportJSON} from './src/core/serialization.ts'; console.log(exportJSON(createDemoCurve()));"
```

The fixture comparison needs Node with TypeScript stripping support (verified Node 24.22.1). The Python converter itself has no third-party dependencies. Integration tests compile `tests/protocol_runner.cpp` with the **same `core.cpp` and `protocol.cpp`** as ESP32, in both LOCKED and VIRTUAL_DEMO configurations. Demo tests run export → conversion → staged upload → hash commit → arm/start → local virtual-plant feedback → manual takeover → stop → rejected implicit restart. Locked tests run the same upload and prove that temperature stays unavailable and outputs remain zero.

The native runner has an explicitly test-only `@tick milliseconds` directive to advance the fake clock in 100-ms steps. That directive is not part of the firmware protocol, not compiled into the device, and never enables physical I/O. These tests do not establish real sensor, actuator, Artisan application, or roaster safety behavior.
